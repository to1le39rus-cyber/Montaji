# 04 — QA / ТЕСТ-ПЛАН

Роль-автор: тестировщик. Используется после каждого спринта из `06-EXECUTION-PLAN.md` — не в
конце всего проекта, а инкрементально, чтобы не повторить историю "патч → READY → не работает".

---

## 1. Принцип

Каждая новая фича проверяется по трём осям: **бизнес-инвариант не нарушен** (сверка с
`01-BUSINESS-LOGIC.md`) → **роль видит ровно то, что должна** → **UX не деградировал на iPhone
Safari** (основная платформа).

## 3. Тест-кейсы для гонки при бронировании (инвариант 23)

Критично протестировать до релиза портала магазинов:
1. Два разных аккаунта роли `store` одновременно (в пределах 1 секунды) отправляют
   `bookingRequest` на одну и ту же дату/слот.
2. Ожидаемый результат: только один запрос успешно превращается в `jobs/{id}` через
   `onBookingRequest`, второй — получает явный статус `rejected` с причиной "слот уже занят",
   а не тихо теряется и не создаёт дублирующий монтаж.
3. Проверить именно через Cloud Functions эмулятор с искусственной параллельной отправкой, не
   вручную (руками невозможно гарантированно воспроизвести гонку).

## 4. Регрессионный чек-лист (расширение существующего `tests/final-architecture.test.mjs`)

Добавить в автоматические тесты (Node `--test`) по мере готовности каждого модуля:
- Синтаксис всех новых файлов (`node --check` / `--input-type=module` для ESM) — уже часть
  процесса, продолжать для каждого нового файла.
- Наличие обязательных DOM id для каждого нового экрана (по аналогии с текущим тестом,
  проверяющим "Архив заметок" — именно так в прошлом аудите была поймана регрессия sandbox).
- Firestore rules — тестировать через `@firebase/rules-unit-testing` (официальный пакет для
  юнит-тестов правил без реального проекта) — отдельный тестовый файл
  `tests/firestore-rules.test.mjs`, покрывающий таблицу из раздела 2 построчно.

## 5. Ручной смоук-тест перед каждым релизом (расширение чек-листа из исходного handoff-документа)

К существующим 27 пунктам добавить:

29. Отправить `bookingRequest`, подтвердить как менеджер, убедиться что `jobs/{id}` появился с
    `createdVia:"storePortal", bookedByStore:true`.
30. Создать срочную заметку с адресатом "конкретный монтажник" — убедиться, что второй
    монтажник её не видит, а адресат получил push (если Спринт 5 уже реализован).
31. Проверить, что личная заметка одного монтажника не видна в списке у другого монтажника даже
    после обновления страницы (не только в реальном времени, но и при первой загрузке).
32. iPhone Safari, PWA добавлено на главный экран — проверить, что push действительно приходит
    (известное ограничение iOS 16.4+, см. `02-TECH-ARCHITECTURE.md`).

## 6. Критерий "готово к продакшену" для каждого спринта

Спринт считается завершённым только если:
- все пункты соответствующего блока из этого документа пройдены вручную,
- `npm test` зелёный (0 регрессий относительно предыдущего спринта — падения, существовавшие
  ДО спринта, документируются отдельно, не блокируют, но не должны расти в числе),
- ни один бизнес-инвариант из `01-BUSINESS-LOGIC.md` не нарушен.
