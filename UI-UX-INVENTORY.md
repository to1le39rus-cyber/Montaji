# MONТАЖИ АА — UI/UX INVENTORY

> **Канонический инвентарь интерфейса.**
> Этот документ фиксирует, какие экраны, окна, sheets, модальные состояния и системные поверхности существуют в приложении, прежде чем мы начнём делать единый визуальный язык.
>
> Цель: не допустить ситуации «на одном экране модалка одна, на другом такая же, но другая». Все новые UI-поверхности должны либо использовать существующий паттерн, либо сначала быть добавлены сюда.
>
> **Визуальная реализация этого инвентаря регулируется `UI-UX-SYSTEM.md`.**

## 1. Принцип продукта

«Монтажи АА» — рабочее приложение. Оно должно быть одновременно:

- очень красивым;
- быстрым и лёгким;
- очевидным с первого взгляда;
- приятным настолько, чтобы хотелось пользоваться им каждый день;
- с маленькими, аккуратными wow-эффектами;
- без анимационной перегрузки;
- без визуального шума;
- без UI-хаков, дублирующих одну и ту же сущность разными способами.

**Красивый интерфейс здесь не противопоставляется рабочему интерфейсу.** Наоборот: красота должна усиливать скорость, уверенность и удовольствие от работы.

### Wow-принцип

Анимация используется как микровзаимодействие, а не как украшение ради украшения:

- открылось плавно;
- кнопка приятно отреагировала на tap;
- сохранение дало короткую понятную обратную связь;
- выполненный выезд визуально «закрылся»;
- цифры/статусы могут мягко обновляться;
- переходы между состояниями должны ощущаться живыми.

Не допускается: тяжёлый blur везде, бесконечные параллаксы, постоянные observers/timers ради анимации, длинные декоративные эффекты и всё, что заметно бьёт по iPhone/Safari.

## 2. Каноническая навигация

Сейчас в canonical runtime есть пять основных экранов:

| ID | Экран | Назначение | Приоритет |
|---|---|---|---|
| `todayScreen` | **Сегодня** | Что происходит сейчас и ближайшие действия | P0 |
| `scheduleScreen` | **График** | Планирование по дням и нагрузка | P0 |
| `moneyScreen` | **Деньги** | Доходы, расходы, долги и источники | P0 |
| `clientsScreen` | **Клиенты** | Быстрый доступ к базе клиентов | P1 |
| `moreScreen` | **Ещё** | Система, экспорт, backup, аккаунт | P1 |

Нижняя навигация является единым глобальным компонентом и должна иметь одно визуальное поведение на всех экранах.

### Глобальные поверхности

1. **Top bar** — бренд, текущая дата, состояние синхронизации.
2. **Bottom navigation** — 5 разделов.
3. **FAB «＋»** — глобальное добавление выезда/записи.
4. **Toast** — короткая обратная связь после действия.
5. **Modal / bottom sheet** — единый паттерн для контекстных действий.
6. **Backdrop + handle + close** — единый механизм закрытия sheet.

## 3. Экран авторизации

### `authScreen`

Не является частью основной навигации.

Содержит:

- бренд;
- приветственный/рабочий блок;
- поле Email;
- поле Пароль;
- кнопку **Войти**;
- **Регистрация**;
- **Забыли пароль?**;
- сообщение об ошибке/успехе.

### Состояния

- initial;
- ввод данных;
- вход в процессе;
- неверные credentials;
- неверный email;
- аккаунт отключён;
- слишком много попыток;
- нет сети;
- регистрация;
- письмо подтверждения отправлено;
- сброс пароля отправлен;
- Firebase недоступен.

**Будущий UI:** auth должен быть визуально частью той же дизайн-системы, но может иметь отдельную композицию, потому что это входной экран.

## 4. Экран «Сегодня»

### Главная задача

Ответить за несколько секунд на вопросы:

1. Что у меня сегодня?
2. Сколько монтажей?
3. Что с деньгами?
4. Есть ли проблема/просрочка/долг?
5. Что будет дальше?

### Текущие зоны

- Hero с сегодняшней нагрузкой и чистым результатом.
- Доход / расход.
- Индикатор нагрузки.
- Неделя / месяц.
- **Что важно** — insights.
- **Сегодня** — список выездов.
- **Расходы сегодня**.
- **Ближайшие дни**.
- **Заметки**.
- Архив заметок внутри раскрываемого блока.

### Основной компонент

**Job Card — Today variant.**

Карточка должна быть максимально лёгкой и быстро сканироваться. Операционные действия не должны перегружать главный экран.

## 5. Экран «График»

### `scheduleScreen`

Содержит:

- заголовок месяца;
- переключение предыдущий/следующий месяц;
- календарную сетку;
- легенду;
- состояние дня;
- фактическое количество монтажей;
- индикатор замера.

### Действие дня

Tap по дню открывает **Day Sheet**.

Важно: три монтажных окна — это плановые пресеты, а не лимит. 4, 5, 6+ монтажей допустимы. UI никогда не должен показывать «3/3» как потолок.

## 6. Day Sheet — рабочий день

### Тип

**Bottom Sheet / Modal**.

### Назначение

Операционный просмотр конкретного дня.

### Содержит

- дату;
- статистику дня:
  - монтажей;
  - плановую среднюю;
  - свободные плановые окна;
- действия:
  - `＋ Выезд`;
  - `− Расход`;
  - `＋ Заметка`;
- секцию **Плановые окна**;
- секцию **Дополнительные монтажи**;
- секцию **Другие выезды**;
- секцию **История** для выполненных;
- при наличии — banner долга;
- переход **Открыть полный день →**.

### Правило

Day Sheet — рабочая поверхность. Здесь допустимы действия, которые специально не показываются на главном Today.

## 7. Day Archive / «Полный день»

### Тип

**Bottom Sheet / Modal**.

### Назначение

История конкретного дня + деньги.

### Содержит

- дату;
- доход;
- расход;
- чистый результат;
- список выездов;
- список расходов;
- редактирование расхода;
- `＋ Расход за дату`.

Это не отдельный экран навигации. Это контекстное окно выбранного дня.

## 8. Карточка выезда — состояния и варианты

### Canonical Job Card

Одна сущность — одна базовая карточка. Разные поверхности могут иметь варианты плотности:

- `Today / primary` — минимум информации, максимум сканируемости;
- `Day Sheet / compact` — больше контекста;
- `History / compact` — история и результат;
- `Client context` — вариант в карточке клиента, если появится;
- `Detail` — полноценный просмотр.

Нельзя создавать новый визуальный тип карточки только потому, что другой экран «чуть-чуть отличается».

### Информация карточки

Потенциально используются:

- клиент;
- время / слот;
- тип;
- магазин / источник;
- сумма;
- адрес;
- комментарий к монтажу;
- статус;
- дата выполнения;
- долг;
- зачёт замера.

**Комментарий — важная рабочая информация**, а не декоративное поле. В компактной карточке он должен быть доступен через аккуратный раскрываемый preview.

## 9. Job Detail — «Подробнее»

### Тип

**Bottom Sheet / Modal**, read-only по умолчанию.

Открывается из карточки выезда через действие **Подробнее**.

### Содержит

- клиент;
- тип / время / источник;
- статус;
- сумму;
- адрес;
- телефон;
- комментарий;
- Яндекс;
- 2ГИС;
- Позвонить;
- Отправить адрес;
- при возможности — `✓ Выполнено`;
- `Изменить данные`.

### Главное UX-правило

**Подробнее ≠ Редактировать.**

Пользователь сначала смотрит информацию. Если хочет изменить её — явно нажимает `Изменить данные`.

## 10. Job Edit — «Новый выезд / Изменить выезд»

### `jobModal`

Тип: **единый form bottom sheet**.

### Типы записи

- Монтаж;
- Замер;
- Рекламация;
- Доставка;
- Сервис;
- Доход.

### Поля

Базовые:

- дата;
- плановый слот / свободное время;
- клиент / за что;
- телефон;
- сумма;
- адрес;
- источник / магазин;
- статус;
- дата выполнения;
- оплата;
- комментарий.

Для замера:

- стоимость замера;
- оплачен;
- зачёт в монтаж;
- перенос в монтаж.

### Действия

- **Сохранить**;
- **Перенести в монтаж** — только в соответствующем состоянии замера;
- **В архив** — для существующей записи;
- для тестовой записи может появляться отдельное безопасное удаление теста.

### Важное правило

Форма одна. Не создавать отдельные визуальные модалки «для монтажа», «для замера», «для дохода» без реальной необходимости. Меняется контент формы, а не shell.

## 11. Expense — расход

### Текущее состояние инвентаря

`app.js` содержит `openExpense()` и ожидает `#expenseModal`, `#expenseForm`, `#expenseId`, `#expenseDate`, `#expenseAmount`, `#expenseCategory`, `#expenseComment`, но canonical `index.html` на текущем этапе не содержит этой модалки.

**Статус: GAP / требует отдельной реализации.**

Это важно зафиксировать сейчас, чтобы мы не маскировали несовпадение архитектуры UI.

### Планируемый canonical surface

**Expense Sheet**:

- дата;
- сумма;
- категория;
- комментарий;
- сохранить;
- закрыть;
- при редактировании — понятное действие изменения/архивации по бизнес-правилам.

Визуально должен использовать тот же shell, что Job Detail / Job Edit / Day Sheet.

## 12. Note — заметка

### Текущее состояние инвентаря

`app.js` содержит `openNote()` и ожидает `#noteModal`, `#noteForm`, `#noteText`, но canonical `index.html` на текущем этапе не содержит этой модалки.

**Статус: GAP / требует отдельной реализации.**

### Планируемый canonical surface

**Note Sheet**:

- короткий текст;
- сохранить;
- закрыть.

Архивирование заметки сейчас должно оставаться частью существующей note-системы до отдельного бизнес-решения.

## 13. Другие UI surfaces

### Confirm

Единый паттерн подтверждения для потенциально опасных действий.

Содержит:

- короткий заголовок;
- объяснение последствий;
- primary action;
- cancel.

### Action Sheet

Для выбора одного действия из нескольких связанных вариантов.

### Toast

Для короткого результата операции.

### Native file picker

Для импорта/backup. Не стилизовать под фальшивый файловый браузер, если нативный picker решает задачу лучше.

## 14. Системные состояния

Инвентарь должен учитывать не только «идеальный экран», но и:

- loading;
- empty;
- error;
- offline;
- saving;
- saved;
- conflict;
- permission denied;
- disabled;
- completed;
- cancelled.

Каждое состояние должно иметь единый визуальный язык.

## 15. Legacy boundary

`secure-app/` — исторический/legacy слой.

Он не является источником истины для canonical runtime.

Не переносить его UI-паттерны автоматически в новый дизайн только потому, что они уже существуют.

Перед переносом нужно определить, является ли паттерн действительно частью canonical system.

## 16. Правило расширения инвентаря

Если появляется новая фича:

1. определить, существует ли подходящий canonical screen/component/sheet;
2. если существует — использовать его;
3. если не существует — сначала добавить сущность в этот inventory;
4. определить визуальный паттерн в `UI-UX-SYSTEM.md`;
5. только после этого реализовывать UI.

**Никаких скрытых модалок, временных карточек и уникальных компонентов «только для этого места».**
