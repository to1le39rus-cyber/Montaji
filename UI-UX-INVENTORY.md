# MONТАЖИ АА — UI/UX INVENTORY

> **Канонический инвентарь интерфейса.**
> Этот документ фиксирует, какие экраны, окна, sheets, модальные состояния и системные поверхности существуют в приложении, прежде чем мы начнём делать единый визуальный язык.
>
> Цель: не допустить ситуации «на одном экране модалка одна, на другом такая же, но другая». Все новые UI-поверхности должны либо использовать существующий паттерн, либо сначала быть добавлены сюда.

## 1. Принцип продукта

«Монтажи АА» — рабочее приложение. Оно должно быть одновременно:

- очень красивым;
- быстрым и лёгким;
- очевидным с первого взгляда;
- приятным настолько, чтобы хотелось пользоваться им каждый день;
- с маленькими, аккуратными wow-эффектами;
- без анимационной перегрузки;
- без визуального шума;
- без UI-хаков, дублирующих одну и ту же сущность разными способами.

**Красивый интерфейс здесь не противопоставляется рабочему интерфейсу.** Наоборот: красота должна усиливать скорость, уверенность и удовольствие от работы.

### Wow-принцип

Анимация используется как микровзаимодействие, а не как украшение ради украшения:

- открылось плавно;
- кнопка приятно отреагировала на tap;
- сохранение дало короткую понятную обратную связь;
- выполненный выезд визуально «закрылся»;
- цифры/статусы могут мягко обновляться;
- переходы между состояниями должны ощущаться живыми.

Не допускается: тяжёлый blur везде, бесконечные параллаксы, постоянные observers/timers ради анимации, длинные декоративные эффекты и всё, что заметно бьёт по iPhone/Safari.

## 2. Каноническая навигация

Сейчас в canonical runtime есть пять основных экранов:

| ID | Экран | Назначение | Приоритет |
|---|---|---|---|
| `todayScreen` | **Сегодня** | Что происходит сейчас и ближайшие действия | P0 |
| `scheduleScreen` | **График** | Планирование по дням и нагрузка | P0 |
| `moneyScreen` | **Деньги** | Доходы, расходы, долги и источники | P0 |
| `clientsScreen` | **Клиенты** | Быстрый доступ к базе клиентов | P1 |
| `moreScreen` | **Ещё** | Система, экспорт, backup, аккаунт | P1 |

Нижняя навигация является единым глобальным компонентом и должна иметь одно визуальное поведение на всех экранах.

### Глобальные поверхности

1. **Top bar** — бренд, текущая дата, состояние синхронизации.
2. **Bottom navigation** — 5 разделов.
3. **FAB «＋»** — глобальное добавление выезда/записи.
4. **Toast** — короткая обратная связь после действия.
5. **Modal / bottom sheet** — единый паттерн для контекстных действий.
6. **Backdrop + handle + close** — единый механизм закрытия sheet.

## 3. Экран авторизации

### `authScreen`

Не является частью основной навигации.

Содержит:

- бренд;
- приветственный/рабочий блок;
- поле Email;
- поле Пароль;
- кнопку **Войти**;
- **Регистрация**;
- **Забыли пароль?**;
- сообщение об ошибке/успехе.

### Состояния

- initial;
- ввод данных;
- вход в процессе;
- неверные credentials;
- неверный email;
- аккаунт отключён;
- слишком много попыток;
- нет сети;
- регистрация;
- письмо подтверждения отправлено;
- сброс пароля отправлен;
- Firebase недоступен.

**Будущий UI:** auth должен быть визуально частью той же дизайн-системы, но может иметь отдельную композицию, потому что это входной экран.

## 4. Экран «Сегодня»

### Главная задача

Ответить за несколько секунд на вопросы:

1. Что у меня сегодня?
2. Сколько монтажей?
3. Что с деньгами?
4. Есть ли проблема/просрочка/долг?
5. Что будет дальше?

### Текущие зоны

- Hero с сегодняшней нагрузкой и чистым результатом.
- Доход / расход.
- Индикатор нагрузки.
- Неделя / месяц.
- **Что важно** — insights.
- **Сегодня** — список выездов.
- **Расходы сегодня**.
- **Ближайшие дни**.
- **Заметки**.
- Архив заметок внутри раскрываемого блока.

### Основной компонент

**Job Card — Today variant.**

Карточка должна быть максимально лёгкой и быстро сканироваться. Операционные действия не должны перегружать главный экран.

---

## 5. Экран «График»

### `scheduleScreen`

Содержит:

- заголовок месяца;
- переключение предыдущий/следующий месяц;
- календарную сетку;
- легенду;
- состояние дня;
- фактическое количество монтажей;
- индикатор замера.

### Действие дня

Tap по дню открывает **Day Sheet**.

Важно: три монтажных окна — это плановые пресеты, а не лимит. 4, 5, 6+ монтажей допустимы. UI никогда не должен показывать «3/3» как потолок.

---

## 6. Day Sheet — рабочий день

### Тип

**Bottom Sheet / Modal**.

### Назначение

Операционный просмотр конкретного дня.

### Содержит

- дату;
- статистику дня:
  - монтажей;
  - плановую среднюю;
  - свободные плановые окна;
- действия:
  - `＋ Выезд`;
  - `− Расход`;
  - `＋ Заметка`;
- секцию **Плановые окна**;
- секцию **Дополнительные монтажи**;
- секцию **Другие выезды**;
- секцию **История** для выполненных;
- при наличии — banner долга;
- переход **Открыть полный день →**.

### Правило

Day Sheet — рабочая поверхность. Здесь допустимы действия, которые специально не показываются на главном Today.

## 7. Day Archive / «Полный день»

### Тип

**Bottom Sheet / Modal**.

### Назначение

История конкретного дня + деньги.

### Содержит

- дату;
- доход;
- расход;
- чистый результат;
- список выездов;
- список расходов;
- редактирование расхода;
- `＋ Расход за дату`.

Это не отдельный экран навигации. Это контекстное окно выбранного дня.

## 8. Карточка выезда — состояния и варианты

### Canonical Job Card

Одна сущность — одна базовая карточка. Разные поверхности могут иметь варианты плотности:

- `Today / primary` — минимум информации, максимум сканируемости;
- `Day Sheet / compact` — больше контекста;
- `History / compact` — история и результат;
- `Client context` — вариант в карточке клиента, если появится;
- `Detail` — полноценный просмотр.

Нельзя создавать новый визуальный тип карточки только потому, что другой экран «чуть-чуть отличается».

### Информация карточки

Потенциально используются:

- клиент;
- время / слот;
- тип;
- магазин / источник;
- сумма;
- адрес;
- комментарий к монтажу;
- статус;
- дата выполнения;
- долг;
- зачёт замера.

**Комментарий — важная рабочая информация**, а не декоративное поле. В компактной карточке он должен быть доступен через аккуратный раскрываемый preview.

---

## 9. Job Detail — «Подробнее»

### Тип

**Bottom Sheet / Modal**, read-only по умолчанию.

Открывается из карточки выезда через действие **Подробнее**.

### Содержит

- клиент;
- тип / время / источник;
- статус;
- сумму;
- адрес;
- телефон;
- комментарий;
- Яндекс;
- 2ГИС;
- Позвонить;
- Отправить адрес;
- при возможности — `✓ Выполнено`;
- `Изменить данные`.

### Главное UX-правило

**Подробнее ≠ Редактировать.**

Пользователь сначала смотрит информацию. Если хочет изменить её — явно нажимает `Изменить данные`.

---

## 10. Job Edit — «Новый выезд / Изменить выезд»

### `jobModal`

Тип: **единый form bottom sheet**.

### Типы записи

- Монтаж;
- Замер;
- Рекламация;
- Доставка;
- Сервис;
- Доход.

### Поля

Базовые:

- дата;
- плановый слот / свободное время;
- клиент / за что;
- телефон;
- сумма;
- адрес;
- источник / магазин;
- статус;
- дата выполнения;
- оплата;
- комментарий.

Для замера:

- стоимость замера;
- оплачен;
- зачёт в монтаж;
- перенос в монтаж.

### Действия

- **Сохранить**;
- **Перенести в монтаж** — только в соответствующем состоянии замера;
- **В архив** — для существующей записи;
- для тестовой записи может появляться отдельное безопасное удаление теста.

### Важное правило

Форма одна. Не создавать отдельные визуальные модалки «для монтажа», «для замера», «для дохода» без реальной необходимости. Меняется контент формы, а не shell.

## 11. Expense — расход

### Текущее состояние инвентаря

`app.js` содержит `openExpense()` и ожидает `#expenseModal`, `#expenseForm`, `#expenseId`, `#expenseDate`, `#expenseAmount`, `#expenseCategory`, `#expenseComment`, но canonical `index.html` на текущем этапе не содержит этой модалки.

**Статус: GAP / требует отдельной реализации.**

Это важно зафиксировать сейчас, чтобы мы не маскировали несовпадение архитектуры UI.

### Планируемый canonical surface

**Expense Sheet**:

- дата;
- сумма;
- категория;
- комментарий;
- сохранить;
- закрыть;
- при редактировании — понятное действие изменения/архивации по бизнес-правилам.

Визуально должен использовать тот же shell, что Job Detail / Job Edit / Day Sheet.

## 12. Note — заметка

### Текущее состояние инвентаря

`app.js` содержит `openNote()` и ожидает `#noteModal`, `#noteForm`, `#noteText`, но canonical `index.html` на текущем этапе не содержит этой модалки.

**Статус: GAP / требует отдельной реализации.**

### Планируемый canonical surface

**Note Sheet**:

- короткий текст;
- сохранить;
- закрыть.

Архивирование заметки сейчас выполняется прямо из списка через действие `✓`, поэтому отдельное окно архивации не нужно, если UX-тестирование не покажет обратное.

## 13. Test record — безопасное удаление теста

Для тестовой записи предусмотрено специальное действие:

**Удалить тестовый выезд**.

Оно не является частью обычного Job Edit для реальных записей.

Правило: тестовые данные можно удалить физически только при явной маркировке теста. Обычные записи — архивируются, а не удаляются.

## 14. Деньги

### `moneyScreen`

Основные зоны:

- выбранный период;
- итог;
- доход;
- расход;
- долги;
- переключатель периода:
  - сегодня;
  - неделя;
  - месяц;
  - весь период;
- список долгов;
- добавление расхода;
- экспорт;
- доход по источникам;
- история расходов.

---

## 15. Клиенты

### `clientsScreen`

Содержит:

- поиск по имени / телефону / адресу;
- подсказку о формировании базы;
- список клиентов.

### Будущая UX-задача

Клиент должен стать самостоятельной сущностью с понятным переходом к истории его выездов, но только после фиксации модели данных. Не создавать UI, который притворяется CRM, если данных для этого пока нет.

---

## 16. «Ещё» / системные действия

### `moreScreen`

Содержит:

- экспорт Excel/CSV;
- полную резервную копию JSON;
- восстановление JSON;
- аккаунт / выход;
- системную информацию о Firebase и синхронизации.

### Системные поверхности

- native file picker для восстановления JSON;
- native confirm для восстановления backup;
- native confirm для архивации записи;
- toast после успешных/неуспешных действий.

Native dialogs не надо стилизовать притворно, если платформа не требует этого. Но их тексты и момент появления должны быть единообразными.

---

## 17. Toast / feedback

Один canonical Toast-компонент.

Состояния:

- neutral;
- success;
- error;
- offline / warning.

Примеры:

- `Сохранено`;
- `Расход сохранён`;
- `Заметка сохранена`;
- `Запись отправлена в архив`;
- `Адрес скопирован`;
- `Не удалось сохранить`;
- `Нет соединения с общей базой`.

Toast должен быть коротким, заметным и не мешать работе.

---

## 18. Состояния интерфейса

Для **каждого** экрана и компонента в дальнейшем должны быть определены:

- loading;
- ready;
- empty;
- error;
- offline;
- saving;
- saved;
- disabled;
- cancelled;
- completed;
- conflict;
- permission denied;
- no access / unknown profile.

Не должно быть так, что loading красиво продуман на Today, но на Money появляется голый текст «загрузка…».

## 19. Единый Modal / Sheet System

Это один из главных пунктов следующего этапа.

### Canonical shell

Все внутренние sheets используют единый принцип:

```text
Backdrop
└── Sheet
    ├── Handle
    ├── Header
    │   ├── Eyebrow / context
    │   ├── Title
    │   └── Close
    ├── Content
    └── Actions
```

### Варианты shell

Разрешены только несколько намеренно определённых вариантов:

1. **Detail Sheet** — посмотреть;
2. **Edit Sheet** — изменить;
3. **Action Sheet** — выбрать действие;
4. **Day Sheet** — рабочий день;
5. **Form Sheet** — короткая форма;
6. **Confirm** — подтверждение опасного действия.

Если новая задача требует «ещё одну уникальную модалку», сначала проверяем, можно ли выразить её одним из этих вариантов.

## 20. Единая система анимации

Анимации должны быть лёгкими и системными.

### Разрешённые классы движения

- sheet enter/exit;
- button press;
- card press;
- status transition;
- progress/value transition;
- expand/collapse comment;
- navigation transition, если она не ухудшает производительность.

### Правила

- короткие длительности;
- transform/opacity предпочтительнее тяжёлых layout-анимаций;
- `prefers-reduced-motion` обязательно учитывать;
- не запускать бесконечные циклы;
- не использовать MutationObserver как основной механизм анимации;
- не использовать таймеры для постоянного поддержания UI;
- анимация не должна задерживать рабочее действие.

**Цель:** пользователь замечает качество, но не замечает ожидание.

---

## 21. Что сейчас canonical, а что legacy

Canonical runtime начинается с:

`index.html → boot.js → app.js → modules → Firebase`

`boot.js` намеренно остаётся простым. filecite_placeholder

В репозитории также существует каталог `secure-app/` с большим количеством исторических/экспериментальных UI-файлов. Он **не является источником истины для текущего UI** только потому, что в нём есть похожие названия компонентов.

До отдельного решения о миграции нельзя переносить оттуда стили/модалки/поведение «просто потому что они уже есть».

---

## 22. Связь с бизнес-правилами

UI не имеет права менять смысл данных.

В частности:

- 3 плановых окна ≠ лимит 3 монтажа;
- 4/5/6+ монтажей допустимы;
- дополнительные монтажи показываются отдельно от плановых окон;
- доход от монтажа и дополнительный доход не смешиваются в понятии «количество монтажей»;
- комментарий к монтажу — рабочая информация;
- отменённый выезд не должен притворяться активным;
- выполненный выезд имеет историю и финансовый смысл.

## 23. Роли

Роли уже описываются отдельно в `ROLE-UX-CONTRACT.md`, но **UI ролей пока не активируем**.

Когда дойдём до role UI, он должен использовать этот же дизайн-системный слой, а не создавать отдельный визуальный мир для менеджера / монтажника / магазина.

---

## 24. Definition of Done для UI

UI-задача считается завершённой только если:

- она соответствует этому инвентарю;
- использует canonical component/pattern;
- имеет состояния loading/empty/error/offline, если применимо;
- имеет mobile-first поведение;
- не создаёт дубликат уже существующего компонента;
- не добавляет случайные цвета/радиусы/тени/шрифты;
- не меняет бизнес-семантику;
- не использует runtime source-rewrite/Blob/CDN hacks;
- не требует MutationObserver/timer/DOM patch там, где можно решить архитектурно;
- не ломает существующие экраны;
- проходит соответствующие тесты;
- проверен на iPhone/Safari и desktop;
- production не изменяется без отдельного согласования.
