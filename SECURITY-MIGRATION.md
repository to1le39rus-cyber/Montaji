# SECURITY MIGRATION — Монтажи АА

## Цель

Перевести доступ к рабочим данным с временного hardcoded-доступа текущих операторов на ролевую модель Firebase Auth + `users/{uid}` + Firestore Rules.

## Текущее состояние

В `firestore.rules` доступ к `appData/shared` и `appData/notes` пока содержит явный список email двух действующих операторов.

Это **временная совместимость**, а не целевая модель.

Причина, почему это нельзя удалять вслепую: если у действующего аккаунта ещё нет корректного документа `users/{uid}` с `role` и `active`, немедленная замена Rules может лишить рабочие телефоны доступа к данным.

## Что запрещено до проверки

- не менять документы Firestore;
- не удалять hardcoded operator access только ради «чистоты» Rules;
- не переводить production на новые Rules без проверки существующих UID;
- не создавать массовую миграцию пользователей автоматически;
- не менять production deployment во время этой миграции.

## Gate перед изменением Rules

Перед переходом на role-based access нужно подтвердить в Firebase Console/административном контуре:

1. какие UID соответствуют двум действующим операторам;
2. для каждого UID существует `users/{uid}`;
3. поле `role` заполнено допустимым значением;
4. поле `active == true`;
5. при необходимости заполнен `storeId`;
6. оба текущих аккаунта после входа проходят чтение `appData/shared` и `appData/notes`;
7. неавторизованный пользователь не получает рабочие данные;
8. пользователь с ролью `store` не получает внутренние данные команды;
9. менеджер получает ожидаемые права;
10. монтажник получает только ожидаемые рабочие права.

## Целевая модель

```text
Firebase Auth
    ↓
users/{uid}
    ├── role: manager | installer | store
    ├── active: true | false
    └── storeId (для store, если нужен)
    ↓
Firestore Rules
    ↓
рабочие данные
```

UI не является границей безопасности. Даже если интерфейс скрывает раздел, доступ должен быть запрещён Rules.

## План безопасного перехода

### Security Step A — inventory

Снять фактическую матрицу существующих пользователей/UID/ролей без изменения данных.

### Security Step B — rules tests

Добавить/проверить тесты для `manager`, `installer`, `store`, inactive user и unauthenticated user.

### Security Step C — compatibility

Убедиться, что текущие рабочие аккаунты имеют необходимые user profiles.

### Security Step D — preview rules

Проверить Rules на preview/test environment или emulator, не меняя production данные.

### Security Step E — production approval

Только после успешных проверок и отдельного подтверждения заменить временный hardcoded-доступ на role-based правила в production.

## Критерий завершения

Hardcoded operator emails отсутствуют в production Rules, а весь необходимый доступ объясняется только ролью, активностью пользователя и `storeId`.

До выполнения этого gate hardcoded-доступ считается **осознанным migration debt**, а не ошибкой, которую нужно исправлять немедленно.
