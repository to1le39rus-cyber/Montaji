# МОНТАЖИ АА

Production PWA для ежедневной работы монтажной команды: график, выезды, замеры, клиенты, деньги, расходы, долги, заметки и история рабочего дня.

## Философия

Приложение строится как рабочий инструмент, а не как демонстрационный интерфейс.

Главный сценарий:

**запланировал → приехал → выполнил → получил деньги → сохранил историю.**

## Production architecture

- Cloud Firestore `appData/shared` — единый source of truth для монтажей и расходов.
- `appData/notes` — отдельный документ для общих заметок.
- Firebase Email/Password Auth — рабочие аккаунты с подтверждением email.
- `getDocFromServer` + fallback `getDoc` — загрузка shared-данных.
- `onSnapshot` — realtime-синхронизация.
- `runTransaction` — конкурентно безопасные записи.
- `localStorage/sessionStorage` не используются как рабочая база.
- отмена = архивное состояние, а не физическое удаление.
- Firebase Hosting — production-хостинг; Vercel/GitHub Pages не являются production-каналом этого проекта.

## UX contract

### Сегодня

- чистыми за день;
- доход и расходы;
- загрузка дня без искусственного лимита;
- слоты 1–3 — пресеты времени, а не ограничение количества монтажей;
- умные сигналы;
- карточки выездов;
- быстрые действия;
- расходы;
- ближайшие дни;
- общие заметки.

### График

Календарь показывает фактическую занятость дня. Количество монтажей на дату не ограничивается тремя: слоты 1–3 являются только удобными пресетами времени.

### Деньги

- выполненная работа = доход;
- выполненная, но не оплаченная работа = доход + долг;
- расход уменьшает чистый результат;
- история не уничтожается.

### Замер

Замер имеет собственное время, стоимость, оплату и связь с будущим монтажом. Стоимость оплаченного замера может быть зачтена в монтаж.

## QA

Regression tests находятся в `tests/`.

Перед release проверяются:

1. загрузка существующей базы;
2. создание/редактирование/отмена;
3. неограниченное количество монтажей на дату;
4. выполнение и долг;
5. последующая оплата;
6. замер;
7. замер → монтаж;
8. расход;
9. история;
10. заметки;
11. realtime на втором устройстве;
12. offline/error states;
13. Safari mobile;
14. Chrome mobile/desktop.

Подробная матрица: `QA-MATRIX.md`.

## Команда проекта

Проект ведётся по production operating system из `TEAM-OPERATING-SYSTEM.md`: Product Owner, Product Strategist, Principal Architect, Principal Frontend Engineer, UX/UI Director, QA Lead, Security Engineer, Technical Writer и Release Manager.

## Release rule

Новая функция не считается готовой, пока не понятны:

- её бизнес-инварианты;
- её ошибки;
- её влияние на существующие данные;
- её поведение на двух клиентах;
- её поведение после перезагрузки;
- её мобильный сценарий.

## Firebase

`firebase-config.js` содержит публичную клиентскую конфигурацию Firebase. Защита данных обеспечивается Auth/Firestore Rules; перед публичным масштабированием рекомендуется App Check и более строгий доступ.

## Deploy

Production branch: `Astera-smart`.

Production deployment выполняется GitHub Actions через Firebase Hosting и публикает тот же репозиторий, который проходит regression suite.

Перед ручным live smoke-test необходимо дождаться зелёного production deployment и открыть Firebase Hosting URL в Safari/Chrome.
