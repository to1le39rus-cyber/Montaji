# МОНТАЖИ AA — Documentation Conflicts

Дата: 13.09.2026
Ветка: `Astera-smart`

Этот документ фиксирует противоречия между историческими документами проекта и устанавливает, какой смысл считается каноническим до следующего архитектурного этапа.

## 1. Ёмкость / `3/3` — КРИТИЧЕСКОЕ ПРОТИВОРЕЧИЕ

### Старые формулировки

`FINAL_AUDIT.md` и `MONTAZHI-AA-OPERATING.md` описывали дневную ёмкость как 3 монтажных окна и трактовали `3/3` как заполнение дневной ёмкости.

### Каноническое решение

**Жёсткого лимита монтажей в день нет.**

Три окна (`10:00–12:00`, `14:00–16:00`, третий слот) — только удобные пресеты времени.

`3/3` — не ограничение и не запрет на четвёртый, пятый и последующие монтажи. Фактическое количество монтажей в день может быть больше трёх.

Продукт должен разделять:

- фактическое количество монтажей за день;
- фактическую занятость/пересечение времени;
- дополнительный доход;
- среднюю рабочую нагрузку — ориентир около **3 монтажей в день**, а не capacity limit.

### Что меняем

- `FINAL_AUDIT.md` — убрать capacity invariant «3 окна» и старый сценарий `3 выполненных / 0 из 3`.
- `MONTAZHI-AA-OPERATING.md` — убрать формулировку о ёмкости 3 окна.
- QA и код должны проверять возможность 3+ монтажей.

## 2. Auth: Anonymous vs Email/Password

### Старые формулировки

`FINAL_AUDIT.md` и `MONTAZHI-AA-OPERATING.md` описывают Anonymous Auth как текущий рабочий транспорт для двух телефонов.

`README.md` и `CLAUDE_HANDOFF.md` уже описывают Email/Password Auth, а handoff прямо отмечает переход и необходимость проверить auth lifecycle.

### Каноническое решение

Документация должна описывать **фактический текущий runtime**, а не историческую схему. На этапе Step 0 auth считается отдельным объектом аудита: сначала проверяется реальная конфигурация `firebase.json`, UI и lifecycle, затем документация закрепляет результат.

До завершения auth-аудита нельзя возвращать Anonymous Auth в документы как установленный факт.

## 3. Production: Firebase Hosting vs Vercel

### Старые формулировки

`README.md` называет Firebase Hosting production-каналом и исключает Vercel/GitHub Pages из production.

При этом фактическая инженерная история проекта содержит активные Vercel deployment/QA paths и secure-app wrapper.

### Каноническое решение

До отдельного release/deployment-аудита нельзя считать ни одну платформу канонической только по документации.

На Step 0 фиксируем принцип:

**один canonical source → один проверяемый deployment contract → preview/QA → явное production promotion.**

Конкретная роль Firebase Hosting и Vercel будет закреплена после проверки workflows, project settings и entrypoints. Запрещено поддерживать две неэквивалентные production-линии.

## 4. `boot.js` и runtime patching

### Старые формулировки

`FINAL_AUDIT.md` допускает `boot.js` как временный compatibility layer.

`TEAM-OPERATING-SYSTEM.md` также допускает его только до переноса подтверждённых замен в канонический `app.js`.

### Каноническое решение

Это временный технический долг, а не архитектурная норма.

Новая постоянная бизнес-логика в runtime patching запрещена. Следующий этап — инвентаризация всех замен `boot.js`, перенос подтверждённых изменений в canonical runtime, regression tests и удаление patching.

## 5. Source of truth

Документы согласованы:

- Firestore `appData/shared` — основной source of truth;
- `appData/notes` — отдельный bounded dataset;
- `onSnapshot` — realtime;
- `runTransaction` — конкурентные бизнес-записи;
- `localStorage/sessionStorage` не являются рабочей БД.

Это считается стабильным контрактом и не требует изменения на Step 0.

---

## 6. История / удаление

Документы согласованы в базовом принципе:

- отмена — состояние/архив, а не hard delete;
- история рабочих операций не должна уничтожаться физическим удалением.

Отдельно будет проверено, не конфликтует ли permanent delete в `secure-app` для заметок с назначением `appData/notes`. Это не следует автоматически переносить на рабочие выезды.

---

## 7. Финансы

Документы согласованы:

- выполненная работа = доход;
- выполненная, но неоплаченная = доход + долг;
- долг не вычитается из дохода;
- расход — отдельная сущность и уменьшает чистый результат;
- чистыми = доход − расходы.

Этот контракт сохраняется.

---

## 8. Что считается каноном при конфликте

При противоречии документов приоритет такой:

1. фактический код и данные — для определения текущего состояния;
2. `PROJECT-CONTRACT.md` — для целевого контракта проекта;
3. `QA-MATRIX.md` — для проверяемых бизнес-инвариантов;
4. `TEAM-OPERATING-SYSTEM.md` — для процесса разработки/release;
5. остальные исторические audit/handoff документы — как контекст, пока не переписаны.

Нельзя разрешать противоречие молча в коде: сначала фиксируется смысл, затем меняется реализация.

## 9. Ограничение Step 0

На этом этапе не изменяются:

- реальные данные Firestore;
- Firebase project;
- production data;
- рабочие бизнес-операции.

Step 0 — фиксация контракта и документационной правды перед архитектурными изменениями.
