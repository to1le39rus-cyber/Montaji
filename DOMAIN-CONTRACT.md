# МОНТАЖИ AA — Domain Contract

Версия: 1.0
Дата: 19.09.2026
Основание: PROJECT-CONTRACT.md, текущий Astera-smart runtime и backup 19.09.2026.

Этот документ фиксирует доменную модель и допустимые бизнес-операции нового canonical runtime. Он не является миграцией данных и не изменяет существующий Firestore.

## 1. Главный принцип

UI не содержит бизнес-правил.

Поток:

Firebase → Repository → Domain → Screen → Component

Любая бизнес-операция проходит через domain-команду и repository. Повторное нажатие одной и той же команды не должно создавать повторный доход, долг, оплату или расход.

## 2. Job

Канонические поля, которые должны сохраняться при чтении/записи существующих данных:

- id
- date
- slot
- time
- type
- status
- client
- phone
- address
- source
- store
- comment
- price
- paid
- completedDate
- measurePrice
- measurePaid
- measureCredit
- convertedToJobId
- convertedFromMeasureId
- cancelledAt

Новые обязательные поля поверх существующих данных добавляются только отдельной миграцией.

### Типы

- Монтаж
- Замер
- Рекламация
- Доставка
- Сервис
- Доп. доход

Замер не считается монтажом.

Доп. доход не увеличивает монтажную нагрузку.

## 3. Состояния

Минимальные текущие состояния:

- Запланирован
- В пути
- На объекте
- Выполнен
- Отменён
- Перенос

Новый runtime не должен создавать дополнительные статусы только ради UI.

## 4. Команды Job

### createJob(input)

Создаёт одну новую запись.

Правила:
- id уникален;
- дата обязательна;
- тип определяется явно;
- количество jobs на дату не ограничивается;
- slot 1/2/3 — временные пресеты, не capacity;
- повторное создание — отдельная операция и отдельный id.

### updateJob(id, patch)

Изменяет существующую запись.

Правила:
- не создавать новую запись без явной операции;
- не менять исторический id;
- не пересчитывать прошлый доход произвольно.

### completeJob(id, completedDate)

Переводит работу в Выполнен и фиксирует completedDate.

Идемпотентность:
- повторное completion не создаёт новый доход;
- доход рассчитывается по состоянию записи, а не по количеству нажатий.

### cancelJob(id)

Переводит запись в Отменён.

Правила:
- физически не удалять рабочую историю;
- отменённая запись не является доходом;
- повторная отмена не создаёт побочных финансовых операций.

### rescheduleJob(id, newDate, ...)

Если перенос реализуется как изменение существующей записи, сохраняется тот же id.
Если бизнес-сценарий создаёт новую запись, между старой и новой записью должна быть явная связь.

Нельзя автоматически объединять похожие записи по клиенту, телефону или адресу.

### markPaid(id)

Переводит completed job из unpaid в paid.

Правила:
- оплата не создаёт дополнительный доход;
- повторное markPaid безопасно;
- оплаченная незавершённая работа не становится доходом только из-за paid=true.

## 5. Финансы

### isIncome(job)

true только если:
- job не отменён;
- job выполнен.

Для Замера используется measurePrice || price по текущему контракту.

Для остальных типов используется price.

### isDebt(job)

Текущая доменная семантика:
- job выполнен;
- job не отменён;
- job.paid === false.

Долг не вычитается из дохода.

### income

Сумма effectiveIncome всех выполненных и неотменённых jobs.

### expenses

Сумма активных расходов за период.

Отменённые расходы не учитываются.

### net

income − expenses.

### additional income

Доп. доход хранится отдельно от показателя монтажной нагрузки.

Он может входить в общий финансовый income только в соответствии с выбранным финансовым представлением, но не должен смешиваться с количеством монтажей.

## 6. Expense

Канонические поля:

- id
- date
- amount
- category
- comment
- cancelled

### createExpense(input)

Создаёт один расход.

### cancelExpense(id)

Отменяет расход без физического удаления истории.

Повторная отмена безопасна.

## 7. Measurement

Замер — самостоятельная Job-запись с type=Замер.

Самостоятельно сохраняется в истории.

### convertMeasurementToJob(measureId, input)

Создаёт отдельную запись Монтаж.

Должны сохраняться:
- convertedToJobId у замера;
- convertedFromMeasureId у нового монтажа;
- исходный замер;
- measurePrice;
- measurePaid;
- measureCredit;
- source.

Конвертация не удаляет замер.

Повторная конвертация существующего замера должна быть заблокирована или вернуть уже созданный связанный монтаж, но не создать второй монтаж.

## 8. Scheduling

Дата содержит произвольное количество jobs.

slot:
- 1 = 10:00–12:00
- 2 = 14:00–16:00
- 3 = 3-й слот / резерв

Slot используется для планирования и сортировки.

Slot не является лимитом.

При необходимости пользователь может создать 4-й, 5-й и последующие монтажи.

Функция выбора свободного слота должна означать только «следующий свободный preset», а не «день заполнен».

## 9. Notes

Notes — отдельный bounded dataset в appData/notes.

Ошибка notes не должна делать shared недоступным.

Команды:
- createNote
- updateNote
- completeNote
- archiveNote

Realtime notes отделён от realtime shared.

## 10. Clients

Отдельная коллекция clients сейчас не вводится.

Клиенты остаются вычисляемой проекцией из jobs.

Ключ идентификации:
- при наличии телефона — телефон;
- иначе существующая логика client/address должна использоваться осторожно.

Автоматическое объединение двух людей в одного клиента без явного основания запрещено.

## 11. Archive / history

Отмена сохраняет запись.

Физическое удаление не является обычной операцией Job.

Если в будущем понадобится permanent delete:
- отдельная команда;
- отдельное подтверждение;
- отдельный permission;
- аудит влияния на финансовую историю.

## 12. Concurrency

Записи shared выполняются через Firestore transaction.

При конфликте:
- повторно читается актуальное состояние;
- mutation применяется к актуальному состоянию;
- результат записывается transaction.

UI не является источником истины.

## 13. Network failure

Если Firestore недоступен:
- текущая загруженная база не должна визуально превращаться в пустую;
- пользователь получает понятное состояние ошибки;
- destructive write не выполняется без подтверждённого соединения.

## 14. Backup / restore

Backup содержит data + notes.

Restore должен:
1. проверить структуру;
2. проверить типы ключевых полей;
3. показать пользователю, что будет восстановлено;
4. требовать явного подтверждения;
5. не принимать повреждённый или очевидно несовместимый файл;
6. не уничтожать рабочую базу простым невалидным upload.

## 15. Invariants

1. Отменённая работа не является доходом.
2. Невыполненная работа не является доходом.
3. Выполненная работа является доходом независимо от оплаты.
4. Выполненная неоплаченная работа является доходом и долгом.
5. Долг не вычитается из дохода.
6. Расход уменьшает net.
7. Доп. доход не считается монтажом.
8. Замер не считается монтажом.
9. Замер не исчезает при конвертации.
10. Повторное действие не удваивает финансовый результат.
11. История отменённых работ сохраняется.
12. Количество jobs в день не ограничивается.
13. Два клиента должны видеть единый Firestore source of truth.
14. Ошибка notes не ломает shared.
15. Ошибка сети не выглядит как пустая актуальная база.

## 16. Запрещённые архитектурные обходы

- source replacement через boot.js;
- Blob-import для постоянной бизнес-логики;
- параллельные UI runtime для одной сущности;
- второй source of truth;
- бизнес-логика внутри render-функций;
- жёсткий лимит монтажей по количеству slot;
- физическое удаление истории как обычный способ отмены;
- автоматическая миграция/очистка реальных данных без отдельного согласования.
