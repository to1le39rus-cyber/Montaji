# 05 — БУДУЩИЕ ФУНКЦИИ (то, что стоит предусмотреть заранее)

Роль-автор: продуктовый стратег. Задача — не "добавить всё сразу", а заложить в архитектуру
места, куда это можно будет встроить без переписывания фундамента. Ничего из этого не входит в
Спринты 1–7 — это бэклог на осознанный выбор приоритетов позже.

---

## 1. Функции, прямо вытекающие из уже описанной модели (низкая цена добавления)

- **Аналитика по магазинам-источникам.** Раз в `jobs` уже есть `storeId` — почти бесплатно
  получить дашборд "доход/количество монтажей по магазину за период". Полезно для переговоров
  об условиях с партнёрами.
- **Рейтинг/надёжность заявок магазина.** Считать % подтверждённых vs отклонённых заявок на
  сторону магазина, % отмен после подтверждения — данные уже есть в `bookingRequests`, нужен
  только экран.
- **История общения по монтажу.** Прямо на карточке `jobs/{id}` — лог всех заметок/статусов/
  изменений в хронологии (сейчас это разрозненно). Технически — просто новый `activityLog`
  подколлекция под `jobs/{id}/log/{entryId}`.

## 2. Функции среднего приоритета (требуют отдельного модуля, но не меняют фундамент)

- **Маршрутизация / оптимизация выездов.** Учитывая, что уже есть адреса и Яндекс/2ГИС ссылки —
  логичное развитие: утренний маршрут по адресам дня в оптимальном порядке. Интеграция с
  Yandex Routing API или аналогом.
- **Складской учёт материалов** (двери, доборы, фурнитура) — если монтажи связаны с расходом
  материалов, это отдельная сущность `inventory/{itemId}` с привязкой списания к `jobs/{id}`.
  Полезно, если растёте и материалов становится сложно отслеживать "на глаз".
- **Гарантийные обязательства и рекламации как отдельный жизненный цикл**, а не просто заметка —
  если рекламаций становится много, имеет смысл выделить `warrantyCases/{id}` с собственным
  статусом (Открыта → В работе → Закрыта), привязкой к исходному `jobId`, сроками по закону
  (если применимо) и историей. Заметки типа "urgent" из текущей модели — по сути MVP-версия
  этого функционала; можно эволюционировать в отдельную сущность, когда объём вырастет.
- **Электронный акт выполненных работ** — генерация PDF с подписью клиента прямо на телефоне
  (canvas для росписи) сразу после "Выполнено" — устраняет бумажный документооборот. Требует
  Cloud Function для генерации PDF (уже есть аналогичный опыт — навык генерации PDF).
- **Многобригадность.** Поле `assignedInstallerUid` уже заложено в схему (Спринт 1). Когда
  появится третий монтажник — понадобится алгоритм распределения (ручное назначение сначала,
  потом можно автоматизировать по загрузке/геолокации).

## 3. Функции долгого горизонта (требуют пересмотра архитектуры, не делать раньше времени)

- **Мультитенантность** — если вы захотите продавать это же приложение другим монтажным
  бригадам как отдельный продукт (не только "Монтажи АА" для себя) — потребует полного
  пересмотра модели данных под `tenants/{tenantId}/jobs/...` вместо плоских коллекций. Не
  начинать это, пока не появится реальный второй клиент — преждевременная абстракция дороже,
  чем рефакторинг по факту необходимости.
- **Открытое API / webhook для интеграций** с внешними системами магазинов (например, если у
  крупного партнёра есть своя CRM и он хочет получать статус монтажа автоматически, не заходя в
  ваш портал). Cloud Functions HTTP-триггеры под это уже архитектурно совместимы, когда
  понадобится.
- **Payroll / расчёт зарплаты монтажников** от количества/суммы выполненных монтажей —
  чувствительная область (деньги сотрудникам), делать только по прямому запросу, не "заранее
  предугадывая", так как формула оплаты — это ваше бизнес-решение, а не техническое.

## 4. Функции, о которых стоит подумать, но НЕ технические — организационные

- **Онбординг нового магазина-партнёра.** Кто создаёт аккаунт, кто объясняет, как пользоваться
  порталом — нужен минимальный "гайд на одну страницу" (не входит в код приложения, но входит в
  успешный запуск функции).
- **Что происходит, если магазин перестаёт быть партнёром.** `active:false` у пользователя,
  `active:false` у `stores/{id}` — предусмотрено схемой, но нужен явный процесс "офбординга",
  не только техническая возможность.

## 5. Явно НЕ рекомендую делать (антипаттерны для такого масштаба команды)

- Не переходить на фреймворк (React и т.п.) только потому что "так принято в больших проектах" —
  для команды из вас + агента вес фреймворка не окупается, вернитесь к этому решению только если
  наймёте штатную фронтенд-команду.
- Не строить мультитенантность заранее "на всякий случай" — см. пункт 3.
- Не автоматизировать распределение бригад до того, как появится реальная третья бригада —
  алгоритм без данных для калибровки будет хуже, чем ручное решение менеджера.
