# 01 — БИЗНЕС-ЛОГИКА И СТРАТЕГИЯ

Роль-автор: бизнес-аналитик / продуктовый стратег. Источник истины при конфликте трактовок.

---

## 1. Продукт одним предложением

Внутренний рабочий инструмент двух монтажников и менеджера для управления графиком, деньгами и
историей, расширенный контролируемым партнёрским доступом для магазинов-источников заказов —
без потери скорости и простоты для монтажника на телефоне.

## 2. Роли и их мотивация (зачем каждой роли то, что ей дано)

### Монтажник
Хочет: быстро увидеть, куда ехать сегодня, отметить статус, не потерять оплату/долг, не забыть
важное (заметки), не листать лишнее.
Не хочет: сложных экранов, множества полей, необходимости объяснять магазину по телефону
"есть ли окно на вторник" — это должно решаться без него.

### Менеджер
Хочет: видеть всё, что видит монтажник, плюс — разруливать конфликты (переадресация задач,
подтверждение заявок от магазинов, разбор рекламаций), общую финансовую картину.
Отличие от монтажника — не в объёме данных (видит то же), а в наборе действий (подтверждение,
назначение, деактивация доступа).

### Магазин (партнёр)
Хочет: не звонить, чтобы узнать свободна ли дата — посмотреть самому. Забронировать. Быть
уверенным, что его слот не "уйдёт" другому магазину, пока он думает.
Не должен: видеть чужих клиентов, чужие цены, внутренние комментарии команды, финансы.

## 3. Бизнес-инварианты (расширение оригинального списка из 20 пунктов под роли)

Исходные 20 инвариантов (см. первый handoff-документ проекта) остаются в силе без изменений.
Добавляются новые, специфичные для многоролевой модели:

21. Магазин не может увидеть ни одного монтажа/клиента другого магазина — ни при каком сценарии,
    включая ошибки конфигурации (обеспечивается архитектурой `publicSlots`, см. 02-TECH-ARCHITECTURE.md,
    а не только правилами доступа).
22. Заявка от магазина (`bookingRequests`) не становится монтажом автоматически — обязательное
    подтверждение человеком (монтажником или менеджером). Это защищает от заявок-ошибок и
    сохраняет контроль над графиком у команды.
23. Два магазина не могут одновременно забронировать один и тот же свободный слот — гонка
    разрешается на уровне транзакции сервера (Cloud Function), а не клиента.
24. Личная заметка монтажника не видна ни другому монтажнику, ни менеджеру, ни магазину —
    без исключений, включая административный доступ (менеджер видит только факт существования,
    не содержание, если явно не потребуется иное решение от вас).
25. Срочная заметка (рекламация) с привязкой к магазину видна этому магазину только в части,
    которую вы явно решите показывать (по умолчанию — заголовок и статус, не внутренние
    комментарии команды, если не указано обратное при создании).
26. Деактивация доступа пользователя (`active: false`) не удаляет его исторические действия
    (кто что создал/изменил) — только блокирует новый доступ.
27. Роль назначается только менеджером вручную. Новый аккаунт по умолчанию — `pending`, без
    доступа ни к чему, кроме своего профиля, до ручного подтверждения.

## 4. Ключевые пользовательские сценарии (для проверки на каждом спринте)

**Сценарий А — монтажник закрывает день.**
Утро → видит список на сегодня → едет → "В пути" → "На объекте" → "Выполнено" → отмечает
оплату/долг → если не успел на следующий монтаж — оставляет заметку/переадресует.

**Сценарий Б — магазин бронирует.**
Заходит в свой личный (урезанный) вход → видит календарь только со статусами занято/свободно →
выбирает дату → отправляет заявку с комментарием → видит статус "На рассмотрении" → получает
подтверждение (push/статус в интерфейсе) → видит, что дата теперь "занята" в его личном списке.

**Сценарий В — рекламация.**
Монтажник или магазин создаёт срочную заметку с привязкой к монтажу → выбирает, кому она видна
(конкретный монтажник / все) → адресат получает push → открывает → либо решает, либо
переадресует другому монтажнику с комментарием → менеджер в любой момент видит полную историю
переадресаций.

**Сценарий Г — менеджер контролирует нагрузку.**
Видит все заявки от магазинов, ожидающие подтверждения → видит все открытые срочные заметки и
на ком они сейчас "висят" → может вручную переназначить.

## 5. Что НЕ входит в бизнес-логику первой версии (сознательное ограничение, не забывчивость)

- Онлайн-оплата через приложение — не входит; оплата остаётся оффлайн, приложение только
  фиксирует факт.
- Автоматическое распределение монтажей между несколькими бригадами — сейчас команда из двух
  человек, поле `assignedInstallerUid` заложено в схему на будущее, но логика распределения не
  строится сейчас (см. `05-FUTURE-FEATURES.md`).
- Юридически значимые документы (акты, договоры) — не входит на этом этапе.

Эти ограничения явные и обсуждаемые — не "забыли", а "сознательно не сейчас", чтобы не размывать
фокус первой версии.
