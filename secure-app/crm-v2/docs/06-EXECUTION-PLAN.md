# 06 — ПОШАГОВЫЙ ПЛАН ИСПОЛНЕНИЯ (для ИИ-агента)

Роль-автор: технический директор / PM. Каждый шаг — самодостаточная задача, которую можно
скормить агенту отдельно, с указанием, какие файлы из пакета ему нужны на этом шаге.

**Правило для агента на каждом шаге:** сначала прочитать, потом менять. Не пропускать
верификацию (раздел "Проверка" в каждом шаге) перед переходом дальше. При любом конфликте —
`01-BUSINESS-LOGIC.md` побеждает.

## ШАГ 3 — Миграция данных (на staging/sandbox проекте, НЕ на реальном `montaj-39` без вашего
отдельного подтверждения)

**Задача агенту:** запустить `migrate-jobs.mjs --dry-run`, показать вам план, дождаться
подтверждения, только потом `--apply`. Это прямое требование политики "не трогать реальные
данные без явной команды" из вашего исходного handoff-документа проекта.

**Файлы агенту:** `migrate-jobs.mjs`, `SCHEMA.md`.

**Проверка:** сверка сумм (уже встроена в скрипт), сверка количества документов, ручная
выборочная проверка 5–10 случайных монтажей "было / стало" бок о бок.

## ШАГ 4 — UI монтажник/менеджер поверх новой схемы

**Задача агенту:** переписать слой чтения/записи в `app.js`-эквиваленте так, чтобы он работал с
коллекцией `jobs/{id}` вместо массива `appData/shared.jobs[]` — **без runtime string-patching**,
обычным модулем (см. `02-TECH-ARCHITECTURE.md`, раздел 2 и 3 про целевую файловую структуру).
UI-паттерны (карточки, статусы, модалки) — переиспользовать существующие CSS-классы, не
изобретать заново (см. `03-DESIGN-SYSTEM.md`, раздел 1).

**Файлы агенту:** `02-TECH-ARCHITECTURE.md`, `03-DESIGN-SYSTEM.md`, текущий `app.js` (как
референс бизнес-логики расчётов — freeSlot, montageCount, финансы — эта логика переносится, не
переписывается заново).

**Проверка:** полный ручной чек-лист из `04-QA-TEST-PLAN.md`, раздел 5, пункты 1–27 (исходные,
без ролевых — на этом шаге роли ещё не в UI).
