## 1. Стек — оставляем как есть, не меняем ради смены

- Firebase (Firestore, Auth, Hosting, Cloud Functions — последнее нужно добавить, сейчас не
  используется вообще).
- Frontend: чистый JS (без фреймворка) — это осознанное решение, менять на React/Vue сейчас
  нецелесообразно: команда — вы + агент, а не команда фронтенд-разработчиков; фреймворк добавит
  сборку/тулинг ради выгоды, которая на этом масштабе не окупится.
- Vercel — для preview/QA деплоя sandbox, Firebase Hosting — production. Оставляем как есть
  (см. предыдущий аудит, раздел про deployment contract — сначала навести порядок там, не тут).

## 2. Главный архитектурный принцип, который нужно закрепить raз и навсегда

**Отказ от runtime string-patching (`boot.js`, заменяющий текст `app.js` через `.replace()`).**

Это было корнем всех найденных в аудите проблем (auth-регрессия в sandbox, потеря заметок).
Для CRM-версии с ролями, порталом магазинов и push-уведомлениями этот паттерн станет source of
truth для критических багов безопасности — недопустимо.

Замена: **обычные ES-модули**, подключаемые напрямую в `index.html`, без пересборки текста в
браузере. Если нужна условная логика (например, разный UI для роли `store`), она реализуется
как обычное ветвление в коде (`if (me.role === 'store') ...`), а не как патч поверх текста.

## 3. Структура файлов (целевая, после Спринта 3)

```
/index.html              — общий вход, определяет layout, роль после логина решает что показать
/app-core.js              — общая логика: auth, роутинг между экранами, данные jobs/expenses
/app-installer.js         — UI, специфичный для installer/manager
/app-store.js              — упрощённый UI для роли store (календарь + бронирование)
/notes-v3.js               — единый модуль заметок (уже готов)
/firebase-init.js          — единственное место инициализации Firebase App
/functions/                — Cloud Functions (Node.js)
  index.js
  onJobWrite.js             — триггер: пересобирает publicSlots при любом изменении jobs/*
  onBookingRequest.js       — подтверждение заявки → создание jobs/{id} транзакцией
  onUserCreate.js           — создаёт users/{uid} с role: "pending" при первом входе
  sendPush.js               — рассылка FCM при urgent-заметке / переадресации
```

## 4. Cloud Functions — зачем каждая обязательна (не "красиво", а функционально необходима)

- **`onJobWrite`** — единственный способ поддерживать `publicSlots` синхронизированным без
  дублирования логики на клиенте (и без риска, что клиент магазина случайно получит доступ к
  полной коллекции `jobs`, если разработчик забудет какое-то правило).
- **`onBookingRequest`** — превращение заявки в монтаж должно происходить в транзакции на
  сервере (service account), чтобы гарантировать инвариант 23 (гонка при бронировании) —
  клиентский код физически не может это гарантировать при двух одновременных заявках.
- **`onUserCreate`** — без этого любой, кто пройдёт email/password регистрацию, получит
  документ пользователя с ролью по умолчанию — критично, чтобы этой ролью было `pending`,
  а не что-то с доступом.
- **`sendPush`** — рассылка FCM должна идти с сервера (у клиента нет доступа к чужим
  `fcmTokens` по правилам безопасности, и это правильно).

## 5. Auth — что меняется, что нет

Email/Password остаётся как метод входа (подтверждено, что работает и в производственной среде
понятен монтажникам). Для магазинов — тот же метод, аккаунт создаёте вы/менеджер вручную и
передаёте логин/пароль партнёру (проще для первой версии, чем инвайт-ссылки — можно добавить
позже).

## 6. Данные — см. отдельно SCHEMA.md и firestore.rules.v2 (уже переданы)

Этот документ их не дублирует, только объясняет, почему они спроектированы именно так —
см. предыдущее сообщение в переписке, где схема и правила были представлены с обоснованием
(переход от монолитного документа `appData/shared.jobs[]` к коллекции `jobs/{id}` — это то, что
физически делает возможным ограниченный доступ для магазинов через Firestore rules).

## 7. Порядок миграции без риска для текущих данных

1. Новые коллекции создаются параллельно, старый документ не трогается (read-only, `allow write: if false`).
2. `migrate-jobs.mjs --dry-run`, затем `--apply` — с автоматической сверкой сумм на выходе.
3. Приложение переключается на новые коллекции отдельным релизом, после ручной проверки, что
   данные перенеслись 1:1.
4. Старый документ остаётся ещё минимум один рабочий цикл (неделя-две) как страховочная копия,
   прежде чем рассматривать его архивацию (не удаление — см. инвариант 7 из бизнес-документа).

## 8. Безопасность — что проверить отдельно перед продакшеном

- App Check (упомянут как рекомендация в исходном handoff-документе, раздел "Безопасность") —
  стоит включить именно на этом этапе, когда появляется внешний тип пользователя (магазин),
  а не только внутренняя команда.
- HTTP referrer restrictions на Firebase API key — проверить, что домены Vercel preview и
  Firebase Hosting оба явно разрешены (это была одна из гипотез в исходном auth-аудите).
- Firestore rules для `publicSlots`/`bookingRequests` — писать только через Cloud Functions,
  клиенту `allow write: if false` везде, где пишет сервер (уже заложено в `firestore.rules.v2`).
