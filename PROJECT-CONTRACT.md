# PROJECT CONTRACT — Монтажи АА

> Канонический контракт проекта. Если старый документ, комментарий или runtime расходится с этим файлом, приоритет у этого контракта.

## 1. Цель

«Монтажи АА» — рабочее мобильное приложение для управления выездами монтажников, графиком, выполненными работами и деньгами.

Главная цепочка продукта:

**График → Выезд → Выполнение → Деньги → История**

Приоритеты разработки:
1. Надёжность и сохранность данных.
2. Понятная рабочая UX.
3. Безопасность и корректные права доступа.
4. Только затем визуальная полировка и новые функции.

## 2. Канонический источник данных

Firebase Firestore — единственный source of truth для рабочих данных.

Основные документы:
- `appData/shared` — рабочие выезды, доходы и расходы.
- `appData/notes` — общие заметки; логически изолированы от рабочих данных.

Рабочее состояние не хранится в `localStorage` или `sessionStorage`.

Изменения общих данных выполняются через Firestore transaction. Клиенты получают актуальные изменения через realtime `onSnapshot`.

При отсутствии сети или недоступности базы приложение не должно выдавать старые данные за актуальные и не должно выполнять записи.

## 3. Бизнес-модель выездов

Поддерживаемые типы:
- Монтаж
- Замер
- Рекламация
- Доставка
- Сервис
- Доп. доход

Отмена не уничтожает запись: отменённый выезд остаётся в истории/архиве.

Перенос — это изменение рабочего статуса/даты, а не удаление исходной истории.

Замер — самостоятельная сущность рабочего процесса. Он может иметь стоимость, факт оплаты и сумму зачёта в будущий монтаж. Замер не должен автоматически превращаться в монтаж без явного действия.

## 4. Важное правило нагрузки: 3/3 НЕ лимит

**Количество монтажей в день не ограничено.**

Три монтажных окна (`10:00–12:00`, `14:00–16:00`, `3-й слот / резерв`) — это текущие планировочные пресеты/ориентир рабочего дня.

`3/3` означает только:

> **средняя ориентировочная нагрузка — около 3 монтажей в день.**

Это НЕ:
- максимальное количество монтажей;
- запрет на 4-й, 5-й, 6-й и последующие монтажи;
- лимит дохода;
- ограничение количества заявок.

Система обязана позволять иметь 3+ монтажей в один день.

В интерфейсе необходимо различать:
- фактическое количество монтажей за день;
- плановую/среднюю нагрузку ≈3 в день;
- свободные планировочные окна;
- фактический доход;
- дополнительный доход.

Нельзя использовать `c >= 3` как признак «день заполнен» в смысле запрета новых монтажей.

## 5. Деньги

Доход, долги и расходы — разные показатели.

### Доход
Доход учитывается по выполненным и не отменённым работам.

### Долг
Выполненная работа с `paid=false` одновременно:
- входит в заработанный доход;
- формирует задолженность.

### Расход
Расходы учитываются отдельно и не превращаются в отрицательный доход.

### Чистый результат
`чистый результат = доход − расходы`.

Дополнительный доход — отдельная рабочая категория и не должен смешиваться с количеством монтажей.

## 6. Роли

Архитектура предусматривает три роли:

### Монтажник
Видит и ведёт свои выезды, рабочий день и связанные с ними деньги.

### Менеджер
Видит общую загрузку, заявки, график и финансовую картину, может распределять работу.

### Магазин
Видит свои заявки/клиентов и доступные окна для бронирования. Не должен получать лишние внутренние операционные или финансовые данные других ролей.

Ролевая модель должна быть реализована через Firebase Auth + данные пользователя/роль + Firestore Rules, а не через набор захардкоженных email в бизнес-логике.

До завершения ролевой миграции текущая рабочая модель двух телефонов не должна ломаться.

## 7. Планировочные окна

Окна `10:00–12:00`, `14:00–16:00` и `3-й слот / резерв` — планировочные пресеты.

Они используются для удобного планирования, но не являются ограничением пропускной способности.

В будущей ролевой модели менеджер должен видеть реальную загрузку по дням, а магазин — доступные для бронирования окна.

## 8. UX-принципы

Главный экран должен отвечать на вопрос: **что мне делать сегодня?**

Ключевые разделы:
- Сегодня
- График
- Деньги
- Клиенты
- Ещё

Карточка выезда показывает минимум, необходимый для быстрого решения. Подробности и расширенные действия находятся внутри карточки/Day Sheet.

Каждое действие должно иметь понятную обратную связь:
**нажал → выполняется → успешно/ошибка → состояние обновилось.**

Не использовать long-press как обязательный способ доступа к критическим действиям.

## 9. Mobile / PWA

Приложение проектируется прежде всего для телефона.

Обязательные требования:
- safe-area;
- корректный viewport;
- удобные touch targets;
- работа с клавиатурой и модальными sheet;
- корректное восстановление после background/return;
- понятное поведение при плохой сети;
- PWA-идентичность и корректные иконки.

## 10. Архитектура runtime

Каноническая целевая схема:

`index.html → app.js / modules → Firebase`

`boot.js` не должен содержать постоянную бизнес-логику через `source.replace`, Blob-import или другие runtime-патчи.

Старые preview/secure loaders, CDN snapshots и временные patch layers не являются каноническим production runtime.

Если временный patch необходим для диагностики, он должен быть явно временным и не становиться частью production architecture.

## 11. UI / CSS

Должна существовать одна каноническая дизайн-система.

Временные `*-final`, `*-polish`, `*-fix`, `v2` слои сначала инвентаризируются и сравниваются по фактическому использованию, после чего полезный код переносится в канонический слой.

Нельзя удалять такие файлы вслепую.

## 12. Безопасность

- Firebase Auth — основа идентификации.
- Firestore Rules — реальный барьер доступа.
- Секреты не помещаются в репозиторий.
- Публичный доступ не должен давать возможность читать/писать чужие данные.
- Ролевая модель должна быть согласована между UI и Rules.
- Изменение Firebase данных/структуры без отдельного согласования запрещено.

## 13. QA

Минимальный regression-набор:
1. создать выезд → reload → данные сохранились;
2. телефон A создал → телефон B увидел;
3. A отметил «Выполнено» → B увидел;
4. выполненная неоплаченная работа появилась в долгах;
5. оплата долга на одном телефоне отражается на другом;
6. замер связан с будущим монтажом корректно;
7. в один день можно создать 3+ монтажей;
8. отмена сохраняет историю;
9. перенос не уничтожает данные;
10. недоступная сеть не подменяется пустой «успешной» базой;
11. Safari/iPhone/PWA smoke test;
12. повторное нажатие не создаёт дубликаты.

## 14. Deploy / release

Каноническая ветка: `Astera-smart`.

Production pipeline:

`Astera-smart → validation → Firebase Hosting + Firestore Rules`

Vercel может использоваться для preview/QA, но preview не считается production автоматически.

Production не меняется вручную во время разработки.

Перед production-релизом:
- проходят тесты;
- проверяется свежий deployment;
- выполняется smoke test;
- подтверждается отсутствие незапланированных изменений данных.

## 15. Правило безопасной разработки

Перед опасным изменением сначала определить:
- что меняем;
- зачем;
- какие файлы затрагиваются;
- что может измениться для пользователя;
- как откатить.

Нельзя:
- переписывать приложение с нуля без необходимости;
- менять Firebase данные без явного разрешения;
- удалять legacy-файлы без проверки зависимостей;
- маскировать ошибки сети пустой базой;
- вводить бизнес-лимиты, которых нет в контракте;
- считать `3/3` жёстким лимитом.
