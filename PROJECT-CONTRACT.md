# МОНТАЖИ AA — Project Contract

Версия: 1.0
Дата: 13.09.2026
Каноническая ветка: `Astera-smart`

Это единый контракт проекта. Он описывает целевую бизнес-модель, архитектуру и правила изменений. Если другой документ противоречит этому файлу, противоречие должно быть зарегистрировано и устранено, а не интерпретировано разработчиком на своё усмотрение.

## 1. Цель продукта

«МОНТАЖИ AA» — рабочее мобильное PWA для монтажной команды.

Главный сценарий:

**запланировал → приехал → выполнил → получил деньги → сохранил историю.**

Приоритеты:

1. надёжность ежедневной работы;
2. сохранность данных;
3. скорость и простота на телефоне;
4. понятные деньги и история;
5. только затем визуальная полировка и новые функции.

Приложение не должно превращаться в CRM-монстра.

## 2. Каноническая бизнес-модель

### 2.1 Монтажи

Количество монтажей на одну дату **не ограничено жёстким максимумом**.

Три привычных времени — это пресеты:

- 10:00–12:00;
- 14:00–16:00;
- третий слот.

Они не являются capacity limit. При необходимости пользователь может создать 4-й, 5-й и последующие монтажи.

Показатель около **3 монтажей в день** трактуется как средняя/ориентировочная рабочая нагрузка, а не как запрет на превышение.

Продукт не должен использовать формулировки «день заполнен на 3/3» как блокирующее бизнес-правило.

### 2.2 Разделяемые метрики

Система должна различать:

- фактическое число монтажей за день;
- плановые временные окна;
- выполненные работы;
- оплаченные и неоплаченные работы;
- долги;
- расходы;
- дополнительный доход;
- среднюю нагрузку около 3 монтажей/день.

Средняя нагрузка — аналитический ориентир, не capacity.

### 2.3 Типы выездов

- Монтаж
- Замер
- Рекламация
- Доставка
- Сервис
- Доп. доход

Замер — отдельная сущность и история.

## 3. Финансовый контракт

1. Отменённая работа не считается доходом.
2. Невыполненная работа не считается доходом.
3. Выполненная работа считается доходом независимо от оплаты.
4. Выполненная, но неоплаченная работа одновременно формирует долг.
5. Долг не вычитается из дохода.
6. Расход — отдельная финансовая сущность.
7. Расход уменьшает чистый результат.
8. **Чистыми = доход − расходы.**
9. Дополнительный доход учитывается отдельно от монтажной нагрузки.
10. Повторное бизнес-действие не должно удваивать доход, долг, оплату или расход.

## 4. Замер → Монтаж

Замер сохраняется самостоятельно.

Явная конвертация создаёт отдельную запись монтажа и сохраняет связь:

- `convertedToJobId`;
- `convertedFromMeasureId`.

Исходный замер не удаляется.

Поля стоимости, оплаты и `measureCredit` не должны теряться при конвертации.

## 5. История и архив

Рабочая история не уничтожается физическим удалением.

Отмена выезда — архивное/отменённое состояние.

Любая операция, которая потенциально удаляет данные, должна быть явно ограничена своей сущностью и проверена на соответствие этому контракту.

## 6. Source of truth и данные

Основной source of truth:

**Cloud Firestore `appData/shared`.**

Отдельный bounded dataset:

**Cloud Firestore `appData/notes`.**

Правила:

- Firestore — рабочая база;
- `onSnapshot` — realtime;
- `runTransaction` — конкурентно безопасные бизнес-записи;
- server-backed загрузка не должна подменяться локальной БД;
- `localStorage/sessionStorage` не используются как рабочий source of truth;
- ошибка notes не должна делать shared недоступным;
- ошибка сети не должна выглядеть как пустая актуальная база;
- существующие реальные данные не мигрируются/не очищаются без отдельного согласования.

## 7. Роли

Целевая ролевая модель:

### Монтажник

Видит:

- свой день;
- свои выезды;
- свои действия;
- свои деньги/долги в рамках разрешённого доступа;
- историю.

### Менеджер

Видит:

- все выезды;
- загрузку по дням;
- свободные окна;
- распределение;
- деньги и рабочие показатели.

### Магазин

Видит:

- свои заявки;
- доступные окна;
- резервирование окна;
- своих клиентов.

Внутренние операционные детали, не необходимые магазину, наружу не выводятся.

Ролевая модель должна быть реализована согласованно с Firebase Auth/Firestore Rules и текущими данными. Нельзя оставлять параллельно конфликтующие модели доступа.

## 8. Frontend architecture

Целевое направление:

`index.html → canonical app.js/modules → Firebase`

`boot.js` не должен содержать постоянную бизнес-логику через source replacement, Blob/import или иные runtime patches.

До полного переноса он может существовать только как временный compatibility-loader с ограниченным контрактом и regression test на каждую существенную замену.

Цель — один canonical runtime без параллельных поколений приложения.

## 9. UI/UX contract

Главная задача интерфейса — дать ответ за секунды:

- что сегодня;
- куда ехать;
- что уже выполнено;
- сколько заработано;
- сколько потрачено;
- что осталось неоплаченным.

Карточка выезда показывает только необходимое для быстрого действия. Подробности открываются в Day Sheet/деталях.

Каждое бизнес-действие должно иметь понятный цикл:

**нажатие → loading → подтверждение → новое состояние.**

Long press не является обязательным способом управления.

Mobile contract:

- iPhone Safari/PWA first;
- safe-area;
- `100svh`;
- крупные touch targets;
- клавиатура не должна ломать форму;
- ошибки сети должны быть понятны;
- после возврата из background состояние должно быть корректным.

## 10. Security contract

Доступ к данным должен определяться Auth + Firestore Rules + ролью/активностью пользователя, а не набором устаревших hardcoded email-исключений.

До публичного масштабирования требуется усиленный security posture: контролируемая аутентификация/роли и при необходимости App Check.

Firebase client config может находиться на клиенте; секреты сервера — нет.

Backup/restore не должен позволять случайному или повреждённому файлу уничтожить рабочую БД.

## 11. QA contract

Критические сценарии:

1. загрузка существующей базы;
2. создание и редактирование;
3. несколько монтажей в один день, включая 3+;
4. выполнение;
5. долг;
6. оплата долга;
7. замер;
8. замер → монтаж;
9. расход;
10. история/отмена;
11. заметки;
12. realtime на втором телефоне;
13. reload;
14. network/database failure;
15. повторное действие;
16. Safari mobile;
17. Chrome;
18. backup/restore.

Статический тест не заменяет live smoke-test.

## 12. Deployment contract

Должен существовать один понятный путь:

**canonical branch → preview → regression/QA → явное production promotion.**

Не допускаются:

- скрытый production runtime patch;
- stale CDN runtime вместо canonical source;
- две неэквивалентные production-линии;
- ручная правка production, не отражённая в Git.

Роль Vercel и Firebase Hosting должна быть явно определена release-процессом после отдельного deployment-аудита.

До этого production не меняется ради Step 0.

## 13. Правила безопасных изменений

Перед рискованным изменением:

1. определить нарушенный контракт;
2. проверить текущий код и deployment;
3. оценить влияние на существующие Firestore данные;
4. при необходимости сделать rollback checkpoint/branch;
5. изменить источник проблемы, а не маскировать симптом;
6. добавить regression test;
7. проверить preview;
8. провести live smoke-test;
9. только после явного согласования менять production.

Запрещено:

- создавать новую Firebase project без необходимости и согласования;
- очищать реальные данные ради теста;
- создавать `app-vN`/`vN.js` как новый слой вместо исправления canonical runtime;
- добавлять второй source of truth;
- превращать 3/3 в жёсткий лимит;
- удалять историю ради упрощения UI;
- чинить runtime patching новым runtime patching.

## 14. Roadmap

0. Зафиксировать контракт и документационные противоречия.
1. Полностью инвентаризировать runtime, Firebase, deployment, CSS и legacy.
2. Сделать canonical runtime и убрать постоянный runtime patching.
3. Привести бизнес-логику к контракту: unlimited daily count + average load ≈3/day, финансы, долги, расходы, замеры, отмены, история.
4. Упростить UX: Today, карточки, Day Sheet, быстрые действия, календарь, деньги, клиенты, добавление.
5. Реализовать согласованную модель ролей.
6. Свести UI в единый design system.
7. Унифицировать Auth/Rules/backup и security posture.
8. Провести реальный E2E/mobile QA.
9. Зафиксировать единый release/deployment pipeline.
10. Выполнить финальный production audit.

## 15. Definition of Done

Проект считается приведённым к этому контракту, когда:

- canonical runtime один;
- бизнес-правила едины в коде, тестах и документации;
- 3+ монтажей в день работают корректно;
- средняя нагрузка ≈3/day не используется как лимит;
- два телефона видят один source of truth;
- деньги/долги/расходы не дублируются;
- история сохраняется;
- auth и Rules согласованы;
- мобильный Safari проходит smoke-test;
- preview и production являются воспроизводимыми сборками из Git;
- временные compatibility/runtime patches удалены или имеют строго ограниченный документированный остаток.


## Производительность и локальный кэш

- Canonical runtime должен поддерживать быстрый старт: последний локальный snapshot интерфейса/данных может показываться сразу, пока Firebase в фоне проверяет актуальность.
- Локальный кэш не является источником истины. Источник истины — Firestore.
- Кэширование не должно подменять realtime-синхронизацию и не должно позволять устаревшим данным незаметно становиться актуальным состоянием.
- В настройках приложения должна быть явная команда **«Очистить локальные данные / кэш»**. Она очищает только локальные данные приложения, не изменяя Firestore, после чего приложение повторно загружает актуальное состояние.
- Кэш приложения должен учитывать версию runtime/assets, чтобы после обновления приложения пользователь не оставался на старом интерфейсе из-за устаревших JS/CSS/assets.
