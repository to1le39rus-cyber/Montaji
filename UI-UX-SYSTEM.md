# МОНТАЖИ АА — UI/UX SYSTEM

> **Каноническая дизайн-система и UX-контракт приложения.**
>
> Этот документ является источником истины для будущих UI/UX-изменений, в том числе для новых AI-чатов и разработчиков. Перед созданием или изменением интерфейса необходимо ознакомиться с `UI-UX-INVENTORY.md`, `UI-UX-SYSTEM.md`, `PROJECT-CONTRACT.md`, `BUSINESS-SEMANTICS.md` и релевантным UX-контрактом.
>
> **Статус:** design direction + implementation contract. Это не разрешение на изменение production.

---

## 1. Визия продукта

«Монтажи АА» должен выглядеть и ощущаться как продукт, которым хочется пользоваться каждый день.

Не «просто рабочая программа». Не «типичный админский dashboard». Не набор таблиц и форм.

### Наше ощущение

**Premium · Clear · Fast · Alive · Calm · Useful**

Пользователь должен одновременно чувствовать:

- «Это очень красиво»;
- «Я сразу понимаю, что происходит»;
- «Я могу сделать действие одним движением»;
- «Приложение реагирует на меня»;
- «Здесь ничего лишнего»;
- «Оно не тормозит».

### Главный принцип

**Красота не конкурирует с рабочим UX. Красота усиливает рабочий UX.**

Каждая визуальная деталь должна помогать хотя бы одному из трёх:

1. понять;
2. выбрать;
3. сделать.

Если декоративный эффект не помогает ни одному из них — он не должен появляться автоматически.

---

## 2. Что мы строим

Это mobile-first рабочее приложение для реальной ежедневной работы.

Основной сценарий должен занимать минимум когнитивных шагов:

**увидел → понял → нажал → получил результат.**

Не заставляем пользователя искать очевидное, читать инструкции там, где достаточно хорошей визуальной иерархии, или открывать пять окон ради одного действия.

### Не превращаем приложение в

- корпоративную CRM с мелким текстом и таблицами;
- перегруженный BI-dashboard;
- коллекцию разношёрстных карточек;
- «красивый» Dribbble-концепт, который неудобно использовать;
- SPA из бесконечных модалок;
- набор временных CSS/JS патчей.

Полный инвентарь находится в `UI-UX-INVENTORY.md`. Здесь фиксируются правила его визуальной реализации.

**Один тип задачи — один визуальный паттерн.**

## 4. Архитектура интерфейса

UI строится слоями:

```text
Business semantics
       ↓
Data / state
       ↓
View model
       ↓
Canonical components
       ↓
Screens / sheets
       ↓
Motion + feedback
```

### Запрещено

- переносить бизнес-логику в CSS;
- вычислять бизнес-правила по DOM;
- дублировать одну сущность в нескольких независимых UI-реализациях;
- создавать отдельную логику для похожих модалок;
- использовать MutationObserver/timer как замену нормальному lifecycle, если задачу можно решить архитектурно;
- добавлять runtime source rewriting, Blob imports, CDN snapshots или подобные обходы;
- создавать «временный» UI без документированного migration plan.

# 5. Визуальный характер

## 5.1 Общая эстетика

Направление: **современный premium mobile product**.

Ключевые свойства:

- чистые поверхности;
- выразительная типографика;
- мягкая глубина;
- аккуратные контрасты;
- много воздуха;
- компактные, но не тесные карточки;
- точечные акцентные цвета;
- качественные иконки;
- деликатная анимация.

### Важный баланс

Мы не хотим:

> «стерильно минималистично».

Мы хотим:

> **«минимально по количеству элементов, максимально по качеству ощущения».**

---

## 5.2 Цвет

До утверждения финальных hex-значений используются семантические токены, а не цвета по месту.

```text
--color-bg
--color-surface
--color-surface-raised
--color-surface-muted
--color-text
--color-text-secondary
--color-text-muted
--color-border
--color-accent
--color-accent-soft
--color-success
--color-warning
--color-danger
--color-info
```

### Правило

Компонент не должен самостоятельно придумывать цвет.

Например, не:

```css
background: #f4f2ff;
```

а:

```css
background: var(--color-accent-soft);
```

Финальная палитра будет утверждена при visual redesign после аудита существующих `styles.css`, `montaji-design-v2.css`, `premium-field-tech.css` и legacy-слоёв.

---

## 5.3 Типографика

Типографика должна создавать иерархию, а не просто задавать размеры.

Семантические уровни:

```text
Display
H1
H2
H3
Body
Body Small
Label
Caption
Numeric / KPI
```

### Принципы

- большие цифры — для действительно важных показателей;
- вторичный текст не конкурирует с действием;
- подписи короткие;
- не использовать слишком много начертаний;
- длинные тексты не превращать в визуальные стены.

---

## 5.4 Сетка и spacing

Используем единый spacing scale.

Рекомендуемая база:

```text
4  — micro
8  — tight
12 — compact
16 — base
20 — comfortable
24 — section
32 — major
40+ — hero / composition
```

Это не повод механически использовать каждое число. Токены должны обеспечивать ритм.

---

## 5.5 Радиусы

Одна система радиусов:

```text
sm  — small controls
md  — fields / compact cards
lg  — cards / sheets
xl  — hero surfaces
pill — chips / status
```

Не создавать уникальный radius для каждого компонента.

---

## 5.6 Глубина

Глубина должна быть физически правдоподобной, но лёгкой.

Предпочитаем:

- тонкий border;
- мягкую тень;
- небольшое изменение surface;
- умеренный backdrop только там, где он реально нужен.

Не используем blur и shadow как декоративный шум.

---

# 6. Канонические компоненты

## 6.1 Job Card — главный компонент продукта

Одна сущность — одна базовая карточка.

Варианты плотности:

- `Today / primary`;
- `Day Sheet / compact`;
- `History / compact`;
- `Client context`;
- `Detail`.

Меняется плотность и контекст, **не дизайн-язык**.

### Иерархия

```text
Client
↓
Time / type / source
↓
Important status / amount
↓
Comment preview
↓
Secondary information
```

Комментарий к монтажу — рабочая информация. Он должен быть заметен, но не превращать карточку в простыню.

### Micro-interactions

- tap feedback;
- аккуратный expand комментария;
- изменение статуса;
- completed state;
- saving/saved feedback.

---

## 6.2 Buttons

Канонические варианты:

```text
Primary
Secondary
Tertiary / Ghost
Danger
Icon
```

### Правила

- один главный CTA на поверхности;
- destructive action визуально отличается;
- иконка без подписи допустима только для очевидного действия;
- tap target должен быть комфортным для пальца;
- disabled — это отдельное состояние, а не просто opacity.

---

## 6.3 Fields

Все поля используют один field system:

```text
Label
Input
Helper / error
State
```

Состояния:

- default;
- focused;
- filled;
- invalid;
- disabled;
- saving;
- saved.

Не делать отдельные стили даты, суммы, телефона и текста без необходимости. Специализированные поля должны быть вариациями одного компонента.

---

## 6.4 Status / Chips

Статус должен читаться за долю секунды.

Используются семантические состояния, а не случайные цвета.

```text
planned
active
completed
cancelled
warning
error
```

Статус никогда не является единственным способом передать критически важную информацию — при необходимости добавляется текстовая формулировка.

---

## 6.5 Toast

Toast — короткая обратная связь, а не место для сложной коммуникации.

Формула:

**что произошло + при необходимости следующий шаг.**

Пример:

`Выезд сохранён`

Не:

`Операция успешно выполнена в базе данных...`

---

# 7. Единая система Modal / Bottom Sheet

Это один из главных контрактов проекта.

## 7.1 Shell

Все sheets используют один базовый shell:

```text
Backdrop
↓
Sheet
 ├─ Handle
 ├─ Header
 ├─ Content
 └─ Actions
```

Едиными должны быть:

- положение;
- радиусы;
- handle;
- backdrop;
- close behavior;
- safe-area handling;
- typography hierarchy;
- vertical rhythm;
- motion.

### Типы содержимого

Один shell, разные purpose:

| Pattern | Для чего |
|---|---|
| Detail Sheet | посмотреть |
| Form Sheet | создать / изменить |
| Action Sheet | выбрать действие |
| Day Sheet | работа с днём |
| Confirm Sheet | подтвердить опасное действие |

Не создавать новый shell ради новой задачи.

---

## 7.2 Detail ≠ Edit

Это обязательное правило.

**Подробнее**:

- read-only;
- информация;
- быстрые действия;
- переход к редактированию.

**Изменить данные**:

- form;
- validation;
- save;
- destructive/archive action при наличии.

Пользователь всегда должен понимать, смотрит он данные или меняет их.

---

# 8. Навигация

Bottom navigation — единый глобальный компонент.

Пять разделов должны иметь:

- одинаковую геометрию;
- одинаковый tap feedback;
- одинаковую active-state механику;
- одинаковую типографику;
- предсказуемое поведение.

### FAB

FAB — глобальное создание записи, если оно доступно текущей роли/контексту.

Он не должен конкурировать с главным CTA конкретного экрана.

---

# 9. Screen-specific UX

## Сегодня

Цель: **понять день за несколько секунд**.

Первый экран должен отвечать:

- что сегодня;
- сколько монтажей;
- что важно;
- что с деньгами;
- какой следующий шаг.

Не перегружать карточки операционными кнопками. Детальные действия находятся в Подробнее / Day Sheet.

## График

Цель: **понять загрузку и выбрать день**.

Три плановых окна — пресеты, а не потолок.

Нельзя визуально кодировать:

`3/3 = закрыто`.

4, 5, 6+ монтажей должны оставаться валидными сценариями.

## Деньги

Цель: **понимать деньги без бухгалтерского перегруза**.

Разделяем:

- доход;
- расход;
- чистый результат;
- дополнительный доход;
- источники;
- долги.

Количество монтажей и доход — разные метрики.

## Клиенты

Цель: **быстро найти человека и его контекст**.

## Ещё

Цель: **системные действия без визуального шума**.

# 10. Motion System — «вау, но быстро»

Motion является частью дизайна, а не последним украшением.

## 10.1 Принцип

**Fast first, delightful second.**

Анимация не должна задерживать действие.

### Базовые категории

```text
Tap
Enter
Exit
Expand
Collapse
State change
Success
Error
Loading
Navigation
```

### Рекомендуемые диапазоны

```text
Micro feedback: 80–140 ms
Small transition: 160–220 ms
Sheet transition: 220–320 ms
Large state transition: 250–400 ms
```

Это ориентиры, а не догма. Реальная motion-система утверждается после прототипирования.

## 10.2 Что создаёт wow

- правильный easing;
- небольшой scale/translate при tap;
- мягкое появление контента;
- последовательное раскрытие информации;
- аккуратное изменение чисел;
- ощущение физической поверхности у sheet;
- выразительное, но короткое success state.

## 10.3 Что запрещено

- бесконечные looping animations без смысла;
- постоянные timers;
- тяжёлый blur на больших поверхностях;
- сложный parallax;
- canvas/WebGL ради обычного UI;
- анимация каждого элемента списка при каждом render;
- motion, которое мешает нажать кнопку;
- анимации, которые ухудшают iPhone/Safari performance.

### Reduced motion

Всегда уважать `prefers-reduced-motion`.

# 11. Состояния интерфейса

Каждый интерактивный компонент должен иметь модель состояний.

Минимальный набор:

```text
initial
loading
loaded
empty
saving
saved
error
offline
disabled
cancelled
completed
conflict
permission-denied
```

### Loading

Не показывать пустой экран, если данные просто загружаются.

Использовать лёгкий skeleton/progressive loading там, где это реально помогает.

### Empty

Empty state должен отвечать:

1. почему здесь пусто;
2. что можно сделать.

### Error

Ошибка должна быть человеческой:

- что произошло;
- можно ли повторить;
- что делать дальше.

### Offline

Offline — состояние продукта, а не исключение, которое нужно прятать.

---

# 12. Accessibility

Красота не должна ухудшать доступность.

Обязательные правила:

- достаточный контраст;
- понятные focus states;
- keyboard support там, где применимо;
- aria-label для icon-only controls;
- понятный текст ошибок;
- touch targets достаточного размера;
- reduced motion;
- не передавать смысл только цветом.

---

# 13. Mobile-first

Основной носитель — телефон.

### Приоритет

1. iPhone Safari / PWA;
2. Android mobile;
3. desktop/tablet enhancement.

Не проектируем сначала desktop, а потом ужимаем.

### Safe areas

Sheets, bottom navigation и FAB должны учитывать safe-area insets.

### Scroll

- один очевидный основной scroll-контейнер;
- не создавать nested scroll без необходимости;
- не ломать scroll при открытии sheet;
- не блокировать iOS gesture navigation.

---

# 14. Performance budget

Premium UI не должен быть тяжёлым.

### Предпочтительно

- CSS transitions;
- transform/opacity для motion;
- минимальные DOM mutations;
- event delegation;
- lazy rendering тяжёлых областей;
- CSS variables;
- reuse компонентов.

### Осторожно

- box-shadow на огромных поверхностях;
- backdrop-filter;
- большие blur areas;
- сложные SVG-фильтры;
- массовые layout-triggering animations;
- повторные Firestore listeners;
- observers, которые вызывают сами себя через DOM mutations.

### Критическое правило

**Если визуальный эффект можно сделать проще без потери ощущения качества — делаем проще.**

---

# 15. Data/UI boundary

UI не является источником истины.

```text
Firestore / canonical state
        ↓
Business rules
        ↓
View model
        ↓
UI
```

Не допускается строить бизнес-решения на основании текста карточки, CSS-класса или наличия DOM-элемента.

### Текущее техническое направление

Комментарий в Job Card уже является важной частью UX. Долгосрочная цель — получать его из canonical state/render path, а не поддерживать отдельный presentation/data bridge, если архитектура позволяет убрать такой bridge без риска.

---

# 16. Business rules, которые UI обязан уважать

### Монтажи

- три окна — плановые пресеты;
- это не capacity limit;
- 4, 5, 6+ допустимы;
- нельзя показывать `3/3` как потолок;
- нельзя блокировать добавление из-за достижения трёх монтажей.

### Доход

- доход не равен количеству монтажей;
- дополнительный доход учитывается отдельно;
- фильтр/аналитика могут показывать доход от монтажей и другие источники независимо.

### Комментарии

Комментарий к монтажу — операционно значимая информация.

---

# 17. Roles

Роли уже описаны отдельно в `ROLE-UX-CONTRACT.md`.

На текущем этапе:

- роль-модель документирована;
- role UI не считается активной частью этого redesign;
- визуальная система должна быть готова к role-specific surfaces;
- нельзя создавать отдельные стили под роль до утверждения role UI.

Безопасность не строится на UI-скрытии. UI ограничивает опыт, Firebase Rules ограничивают доступ.

# 18. Design tokens как контракт

Когда начнётся реализация визуальной системы, токены должны быть вынесены в единый источник.

Минимальные группы:

```text
color.*
type.*
space.*
radius.*
shadow.*
motion.*
z.*
control.*
```

Компонент использует токены, а не собственные значения.

### Пример

```css
.component {
  padding: var(--space-4);
  border-radius: var(--radius-lg);
  color: var(--color-text);
  background: var(--color-surface);
  transition: transform var(--motion-fast) var(--ease-standard);
}
```

# 19. Visual QA

UI считается готовым не тогда, когда «работает», а когда проходит visual QA.

Проверяем:

### Layout

- iPhone narrow;
- standard mobile;
- desktop;
- long content;
- keyboard open;
- safe area.

### States

- loading;
- empty;
- error;
- offline;
- saving;
- completed;
- cancelled;
- conflict;
- permission denied.

### Interaction

- tap;
- long content;
- scroll;
- sheet open/close;
- back gesture;
- keyboard;
- repeated tap;
- rapid navigation.

### Motion

- no jank;
- no layout jumps;
- no animation blocking;
- reduced motion works.

# 20. Definition of Done для UI

UI-фича не считается завершённой, пока:

- [ ] она есть в `UI-UX-INVENTORY.md`;
- [ ] её паттерн определён в `UI-UX-SYSTEM.md`;
- [ ] используется существующий component/shell или документировано расширение системы;
- [ ] нет дублирующего visual pattern;
- [ ] состояния определены;
- [ ] mobile-first проверен;
- [ ] motion проверен;
- [ ] reduced motion учтён;
- [ ] accessibility проверена;
- [ ] performance не ухудшена;
- [ ] business semantics не изменены случайно;
- [ ] Firebase Rules/data не затронуты без отдельного разрешения;
- [ ] production не изменён без явного approval;
- [ ] тесты/проверки пройдены.
